一、网络应用模型

6.1.1 客户/服务器模型

客户/服务器模型概述

客户/服务器 ( Client/Server, C/S ) 模型是网络应用中最早出现也是最经典的架构模式. 在该模型中，网络中的节点被分为两类 :

  • 服务器 ( Server ) : 提供计算资源、数据存储或服务的节点，通常具有固定的、公开的 IP 地址，持续运行，等待客户请求.
  • 客户机 ( Client ) : 主动发起请求的节点，通常是用户终端设备 ( 如 PC、手机 ) ，临时连接到服务器，使用其提供的服务.

服务器的特性

特性 说明
被动等待 服务器不主动发起连接，总是等待客户请求
永久地址 服务器通常具有固定的公网 IP 地址
持续运行 服务器程序通常 24 小时运行
集中管理 所有资源和服务由服务器集中管理和分配
可扩展性差 当客户数量激增时，服务器可能成为瓶颈

客户机的特性

特性 说明
主动发起 客户机主动向服务器发送请求
临时连接 客户机可以在需要时连接，通信结束后断开
本地处理 尽可能在本地完成计算，减少网络流量
不直接通信 客户机之间通常不直接通信，需通过服务器中转

典型应用

应用 服务器角色 客户端角色
Web 浏览 Web 服务器 ( Apache, Nginx ) 浏览器
电子邮件 邮件服务器 邮件客户端
文件下载 FTP 服务器 / 文件服务器 下载工具
数据库 数据库服务器 ( MySQL, Oracle ) 数据库客户端

C/S 模型的优点

  • 集中管理 : 便于对资源访问权限进行控制和数据管理
  • 安全性高 : 通过服务器统一管理安全策略
  • 可靠性强 : 服务器通常具备高可靠性硬件和冗余机制
  • 易于扩展 : 可以在服务器端增加硬件提升性能

C/S 模型的缺点

  • 服务器瓶颈 : 大量客户同时访问时服务器压力大
  • 单点故障 : 服务器崩溃则所有客户无法使用
  • 扩展性差 : 无法应对爆发式增长
  • 成本高 : 需要购置和维护专用服务器设备

6.1.2 P2P 模型

P2P 模型概述

对等网络 ( Peer-to-Peer, P2P ) 模型是一种分散化的网络架构模型. 在 P2P 网络中，每个节点 ( 称为 peer ) 既可以是服务的请求者，也可以是服务的提供者. 节点之间直接共享资源和服务，无需依赖中心化的服务器.

与 C/S 模型的核心区别

维度 C/S 模型 P2P 模型
架构 集中式 分散式
角色 服务器 + 客户机 所有节点对等
资源位置 服务器 分散在各个节点
通信方式 客户 ↔︎ 服务器 任意节点之间
扩展性 差 ( 受服务器限制 ) 好 ( 节点越多资源越丰富 )
可靠性 单点故障 去中心化，无单点故障

P2P 的优势

优势 说明
高扩展性 每个新节点同时带来新的资源，资源与需求同步增长
成本分摊 没有昂贵的服务器，资源由所有节点共同提供
抗攻击 无中心化目标，难以通过摧毁服务器来瘫痪网络
高可靠性 节点冗余，个别节点故障不影响整体服务
负载均衡 流量分散到多个节点，避免单点拥塞

P2P 的挑战

挑战 说明
管理复杂 分散化导致资源管理、版权管理困难
安全威胁 节点行为不可控，可能传播恶意软件
一致性难 数据分散，更新同步困难
性能不稳定 节点随时可能离开，导致下载中断

典型 P2P 应用

应用 说明
BitTorrent P2P 文件共享协议，支持断点续传、多源下载
eDonkey/eMule 电驴/电骡，分布式文件共享
Skype ( 早期 ) P2P 语音/视频通话
区块链 Bitcoin 等加密货币依赖 P2P 网络实现去中心化
IPFS 星际文件系统，分布式存储协议

混合 P2P 模型

在实际应用中，许多系统采用 C/S + P2P 混合架构 :

  • 中心服务器 负责 : 用户认证、索引服务、元数据存储
  • P2P 网络 负责 : 实际数据传输

例如 : QQ、微信 即采用混合模型 : 登录认证服务器是 C/S 结构，但消息传输采用 P2P 直连或中继.

二、域名系统 DNS

6.2.1 层次域名空间

域名系统概述

域名系统 ( Domain Name System, DNS ) 是 Internet 的核心基础设施之一，负责将人类可读的域名 ( 如 www.example.com ) 转换为机器可识别的 IP 地址 ( 如 93.184.216.34 ) . DNS 采用分布式数据库架构，层次化地管理全球的域名映射关系.

域名的层次结构

域名采用树形层次结构，从右到左级别递减，各部分用点号分隔 :

根域名

  • 根域名是 DNS 树的最顶层，用 . 表示 ( 通常省略 )
  • 全球共有 13 组 根域名服务器 ( A~M ) ，由不同组织运营
  • 根服务器知道所有顶级域名服务器的信息

顶级域名 ( Top-Level Domain, TLD )

类别 示例 说明
国家顶级域名 ( ccTLD ) .cn、.jp、.uk 按国家/地区划分
通用顶级域名 ( gTLD ) .com、.org、.net 通用类别
基础设施域名 .arpa 用于反向域名解析
新顶级域名 .app、.xyz、.io 近年新增

二级域名

  • 由注册人向域名管理机构申请获得
  • 例如 : example.com 中的 example 是二级域名
  • 二级域名以下还可以划分子域，形成更细的层次

完整域名的结构示例

域名命名规则

  • 每个部分由英文字母 ( a-z ) 、数字 ( 0-9 ) 和连字符 ( - ) 组成
  • 不区分大小写
  • 每个部分不超过 63 个字符
  • 完整域名长度不超过 255 个字符
  • 不能以连字符开头或结尾

6.2.2 域名服务器

域名服务器分类

DNS 系统包含多种类型的域名服务器，它们各司其职、层次分明 :

服务器类型 作用 管辖范围
根域名服务器 知道所有顶级域名服务器的位置 管理顶级域名 ( TLD )
顶级域名服务器 管理该 TLD 下的所有二级域名 如 .com、.cn、.org 等
权威域名服务器 存放域名→IP 的最终映射 ( DNS 记录 ) 负责特定域名的最终解析
本地域名服务器 递归解析本地域名或转发请求 ISP、企业网络常设

根域名服务器

  • 全球共 13 组 ( 不是 13 台 ) ，编号为 A~M
  • 根服务器 IP 地址相对固定 ( 变化极小 )
  • 所有递归解析都从根服务器开始

顶级域名服务器

TLD 类型 示例 管理者
.com、.net、.edu 通用 Verisign
.org 非营利 Public Interest Registry
.cn 中国 CNNIC
.jp 日本 JPNIC

权威域名服务器

  • 权威 ( Authoritative ) 意味着”对外正式发布”
  • 权威服务器的 DNS 记录被认为是最权威的答案
  • 分为 :
    • 主 ( Master/Primary ) 服务器 : 存放原始 DNS 数据，可读写
    • 从 ( Slave/Secondary ) 服务器 : 从主服务器同步数据，只读

本地域名服务器

  • 也称 递归服务器 ( Resolver )
  • 特点 :
    • 离用户最近 ( 通常在同一 ISP 或企业网络 )
    • 缓存域名解析结果，提高效率
    • 可以配置为递归查询或迭代查询模式

6.2.3 域名解析过程

域名解析类型

DNS 查询分为两种查询方式 :

查询类型 说明 特点
递归查询 DNS 客户端将查询请求完全交给 DNS 服务器，服务器负责全程查询并返回最终结果 对客户端简单，但服务器负载重
迭代查询 DNS 服务器返回最佳答案 ( 如下一个应查询的服务器地址 ) ，客户端自行继续查询 负载分散，但客户端实现复杂

实际解析过程 ( 递归 + 迭代混合 )

大多数 DNS 系统采用 递归查询 + 迭代查询 的混合模式 :

  1. 客户端 → 本地域名服务器 : 递归查询 ( 要求返回最终结果 )
  2. 本地域名服务器 → 根/TLD/权威服务器 : 迭代查询 ( 获取最佳答案 )

完整解析示例

查询 www.example.com 的 IP 地址 :

步骤 查询方向 说明
1 客户端 → 本地域名服务器 发送 www.example.com 查询请求
2 本地域名服务器检查缓存 若已有记录且未过期，直接返回
3 本地域名服务器 → 根服务器 迭代查询 .com TLD 服务器地址
4 根服务器返回 告知 .com TLD 服务器地址列表
5 本地域名服务器 → TLD 服务器 查询 example.com 的权威服务器
6 TLD 服务器返回 告知 example.com 的权威服务器地址
7 本地域名服务器 → 权威服务器 查询 www.example.com 的 IP
8 权威服务器返回 返回 www.example.com → 93.184.216.34
9 本地域名服务器 → 客户端 返回最终解析结果
10 本地域名服务器缓存结果 TTL 时间内再次查询直接返回

DNS 缓存机制

  • DNS 解析结果会被缓存以提高性能
  • 每条记录有 TTL ( Time To Live ) 值，指示缓存有效期
  • 缓存可能造成的问题 :
    • 更新延迟 : 域名 IP 变更后，依赖缓存的客户端可能仍解析到旧 IP
    • 缓存投毒 : 恶意 DNS 服务器返回伪造的 DNS 记录

DNS 记录类型

记录类型 作用 字段示例
A 域名 → IPv4 地址 example.com. IN A 93.184.216.34
AAAA 域名 → IPv6 地址 example.com. IN AAAA 2606:2800:220:1
CNAME 域名别名 www.example.com. IN CNAME example.com.
MX 邮件交换服务器 example.com. IN MX 10 mail.example.com.
NS 域名服务器 example.com. IN NS ns1.example.com.
TXT 文本信息 ( SPF 等 ) 用于验证、垃圾邮件过滤
PTR IP → 域名 ( 反向查询 ) 用于邮件服务器验证等

DNS 协议端口

场景 端口 协议
域名查询 UDP 53 客户端向服务器查询
区域传输 TCP 53 主从服务器同步数据
响应超过 512 字节 TCP 53 大响应必须用 TCP

三、文件传输协议 FTP

6.3.1 FTP 工作原理

FTP 概述

文件传输协议 ( File Transfer Protocol, FTP ) 是 Internet 上历史最悠久、应用最广泛的文件传输协议之一. FTP 采用 客户端/服务器架构，基于 TCP 协议实现可靠的文件传输.

FTP 的工作模式

FTP 使用 控制连接 + 数据连接 的双连接模式 :

连接类型 端口 作用 生命周期
控制连接 21 ( 服务器端 ) 传输命令和响应 整个 FTP 会话期间保持
数据连接 20 或动态 ( 服务器端 ) 传输实际文件数据 按需建立，传输完毕关闭

控制连接

  • 控制连接使用 Telnet 协议 交互命令
  • 命令以 ASCII 文本形式传输 ( 7 位 )
  • 典型命令 : USER、PASS、LIST、RETR、STOR、QUIT
  • 响应码 : 1xx ( 积极初步 ) 、2xx ( 积极完成 ) 、3xx ( 积极中间 ) 、4xx/5xx ( 错误 ) 、5xx ( 永久错误 )

数据连接

数据连接根据传输模式和服务器角色不同，使用不同端口 :

模式 服务器端口 数据流向 说明
主动模式 ( PORT ) 20 服务器主动连接客户端 客户端需开放端口，防火墙不友好
被动模式 ( PASV ) 动态 客户端主动连接服务器 服务器开放随机端口，对客户端友好

6.3.2 控制连接与数据连接

控制连接详解

控制连接是 FTP 会话的管理通道，始终保持开放状态 :

特性

  • 使用 TCP 端口 21 ( 服务器端 )
  • 客户端使用随机高端口连接
  • 基于 Telnet 协议 交互 ( ASCII 文本命令 )
  • 全双工 : 可同时发送命令和接收响应
  • 带外传输 : 命令/响应与数据分离 ( 不同于 HTTP 的请求/响应 )

控制连接命令分类

类别 命令 说明
访问控制 USER, PASS, QUIT, REIN 用户登录/退出
传输参数 PORT, PASV, TYPE, STRU, MODE 数据连接配置
文件操作 RETR, STOR, APPE, DELE, RNFR/RNTO, LIST, NLST 文件操作命令
目录操作 CWD, PWD, CDUP, MKD, RMD 目录管理命令

数据连接详解

数据连接是实际传输文件的通道，按需建立和关闭 :

特性 : - 临时性 : 每传输一个文件 ( 或文件列表 ) 建立一次，传输完毕关闭 - 端口不固定 : - 主动模式 : 服务器用 20 - 被动模式 : 服务器用 随机高端口 - 可传输 : 文件内容、目录列表

数据连接建立规则

模式 数据连接发起方 服务器端口 客户端端口
主动模式 ( PORT ) 服务器 ( 20 ) → 客户端 20 客户端指定 ( 高端口 )
被动模式 ( PASV ) 客户端 → 服务器 ( 高端口 ) 服务器随机开放 客户端随机 ( 高端口 )

两种模式的对比

维度 主动模式 ( PORT ) 被动模式 ( PASV )
服务器端口 固定 20 动态 ( 随机 )
防火墙影响 服务器主动连接可能受阻 客户端主动连接更易穿透
NAT 影响 客户端需端口映射 对 NAT 友好
安全性 较低 ( 服务器主动连接外部 ) 较高

匿名 FTP

  • 某些 FTP 服务器允许 匿名登录 ( 用户名 anonymous )
  • 密码通常用电子邮件地址代替
  • 常用于公开软件仓库、开源项目发布

FTP 与 HTTP 对比

维度 FTP HTTP
协议端口 21 ( 控制 ) 80/443
连接模式 双连接 ( 控制+数据 ) 单连接 ( 请求/响应 )
状态保持 有状态 ( 维持会话 ) 无状态
传输方向 双向 ( 上传/下载 ) 主要是下载
断点续传 支持 ( REST 命令 ) 支持 ( Range 首部 )
目录遍历 支持 ( LIST 命令 ) 不支持

邮件协议栈

协议 方向 端口 作用

POP3 接收 TCP 110 MTA→MUA 下载邮件到本地
IMAP 接收 TCP 143 MTA→MUA 在线查看邮件 ( 同步 )
MIME 编码 — 邮件内容格式 ( 支持多媒体 )

邮件发送流程

以 Alice 发送邮件给 Bob 为例 :

  1. Alice 使用 MUA ( 如 Outlook ) 撰写邮件，填写收件人 bob@example.com
  2. MUA 通过 SMTP 将邮件发送到 Alice 的邮件服务器 ( mail.alice.com )
  3. Alice 的邮件服务器通过 DNS 查询 获取 example.com 的 MX 记录
  4. Alice 的邮件服务器通过 SMTP 将邮件发送到 Bob 的邮件服务器 ( mail.example.com )
  5. Bob 的邮件服务器存储邮件，等待 Bob 来取
  6. Bob 使用 MUA 通过 POP3/IMAP 从服务器 拉取 邮件

6.4.2 电子邮件格式与 MIME

电子邮件格式 ( RFC 822 )

早期电子邮件格式由 RFC 822 规定，邮件分为 首部 ( Header ) 和 正文 ( Body ) 两部分，中间以空行分隔.

邮件首部字段

字段 说明 示例
From 发件人邮箱 From: Alice <alice@example.com>
To 收件人邮箱 To: Bob <bob@example.com>
Cc 抄送 Cc: charlie@example.com
Bcc 密送 ( 隐藏副本，不出现在其他收件人眼中 )
Subject 邮件主题 Subject: 项目计划书
Date 发送时间 Date: Wed, 01 May 2026 10:30:00 +0800
Message-ID 唯一标识 <12345@example.com>
Reply-To 回复地址 Reply-To: alice@gmail.com

邮件正文

  • RFC 822 规定邮件正文只能是 7 位 ASCII 字符
  • 每行不超过 1000 个字符
  • 纯文本格式，不支持多媒体

MIME ( 多用途互联网邮件扩展 )

MIME ( Multipurpose Internet Mail Extensions ) 扩展了 RFC 822 的限制，支持 :

  • 多媒体内容 : 图片、音频、视频
  • 非 ASCII 字符 : 如中文、日文 ( 通过 Base64 编码 )
  • 复杂结构 : 多部分邮件、嵌套

MIME 核心字段

字段 说明 示例
MIME-Version MIME 版本 MIME-Version: 1.0
Content-Type 内容类型 Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding 传输编码 Content-Transfer-Encoding: base64

Content-Type 类型

类型 子类型 说明
text plain, html 纯文本、HTML
image jpeg, gif, png 图片
audio mp3, wav 音频
video mp4, avi 视频
application pdf, zip, octet-stream 应用数据
multipart mixed, alternative, parallel 多部分邮件

Content-Transfer-Encoding 编码方式

编码方式 说明 适用场景
7bit 原始 ASCII，无需编码 纯英文文本
8bit 8 位字符 ( 保留 ) 少量非 ASCII 字符
binary 二进制 特殊协议传输
quoted-printable 可打印字符编码 少量非 ASCII ( 如中文 )
base64 6 位块编码 大量二进制数据 ( 图片、附件 )

Base64 编码示例

多部分邮件 ( Multipart )

multipart/mixed 多个独立部分 带附件的邮件
multipart/alternative 同一内容的多种表示 邮件同时有 Plain 和 HTML 版本
multipart/parallel 并行显示的多部分 需同时显示的多个部分
multipart/related 相关部分 HTML 邮件中内嵌图片

6.5.2 超文本传输协议 HTTP

HTTP 协议概述

超文本传输协议 ( HyperText Transfer Protocol, HTTP ) 是万维网的核心协议，定义了浏览器 ( 客户端 ) 与 Web 服务器之间的通信格式和规则. HTTP 是 无状态、无连接 的应用层协议.

HTTP 版本演进

版本 年份 主要特性
HTTP/0.9 1991 极简协议，只支持 GET
HTTP/1.0 1996 引入首部、状态码，支持多种请求方法
HTTP/1.1 1999 持久连接 ( Keep-Alive ) 、管道化、缓存控制
HTTP/2 2015 多路复用、头部压缩、服务器推送
HTTP/3 2022 基于 QUIC ( UDP ) ，消除队头阻塞

HTTP/1.1 主要特性

特性 说明
持久连接 ( Persistent Connection ) TCP 连接可复用，避免重复三次握手
管道化 ( Pipelining ) 客户端可连续发送多个请求 ( 需按序响应 )
分块传输 ( Chunked Transfer ) 支持流式响应，边生成边传输
虚拟主机 ( Virtual Hosting ) 一台服务器托管多个网站 ( Host 首部 )

HTTP 请求方法

方法 语义 幂等 安全 说明
GET 获取资源 ✓ ✓ 仅读取，不修改资源
POST 提交数据 ✗ ✗ 创建资源、提交表单
PUT 上传资源 ✓ ✗ 替换指定资源
DELETE 删除资源 ✓ ✗ 删除指定资源
HEAD 获取首部 ✓ ✓ 与 GET 类似，但无响应体
OPTIONS 查询能力 ✓ ✓ 查询支持的 HTTP 方法
PATCH 部分更新 ✗ ✗ 修改资源的部分字段

幂等 ( Idempotent ) : 多次执行结果相同. 安全 ( Safe ) : 不修改资源.

HTTP 状态码

类别 含义 典型状态码
1xx 信息性 100 Continue, 101 Switching Protocols
2xx 成功 200 OK, 201 Created, 204 No Content
3xx 重定向 301 Moved Permanently, 302 Found, 304 Not Modified
4xx 客户端错误 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found
5xx 服务器错误 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable

常见状态码详解

状态码 说明 典型场景
200 OK 请求成功 GET 成功、POST 处理成功
201 Created 资源已创建 POST 创建新资源
204 No Content 无内容 DELETE 成功
301 Moved Permanently 永久移动 域名迁移，浏览器自动跳转新 URL
302 Found 临时移动 临时重定向
304 Not Modified 未修改 缓存有效，使用本地缓存
400 Bad Request 请求语法错误 参数错误、格式错误
401 Unauthorized 未认证 需要登录
403 Forbidden 无权限 登录了但无权访问
404 Not Found 资源不存在 页面/接口不存在
500 Internal Server Error 服务器内部错误 代码异常
502 Bad Gateway 网关错误 上游服务器故障
503 Service Unavailable 服务不可用 服务器过载、维护

HTTP 首部字段分类

类别 示例 说明
通用首部 Date, Cache-Control, Connection 请求/响应都可用
请求首部 Host, User-Agent, Accept, Cookie 仅请求中使用
响应首部 Server, Last-Modified, Set-Cookie 仅响应中使用
实体首部 Content-Type, Content-Length, Content-Encoding 描述实体数据
