一、传输层提供的服务

5.1.1 传输层的功能

传输层的地位

传输层位于 OSI 七层模型的第 4 层，介于应用层和网络层之间。它在 端系统（主机）内部 完成端到端的进程间通信，是整个网络体系结构中至关重要的层次。

与网络层的区别

维度 网络层 传输层
作用范围 主机到主机（IP 层） 进程到进程（端到端）
标识 IP 地址（主机） 端口号（进程）
协议 IP（面向无连接） TCP/UDP（TCP 面向连接）
服务类型 不可靠的尽力而为 TCP 可靠 / UDP 不可靠
复用/分用 无 有（多进程复用同一 IP）

传输层的核心功能

1. 复用与分用（Multiplexing & Demultiplexing）

  • 复用：多个应用进程（不同端口）共用同一个传输层协议，通过源端口号区分。
  • 分用：接收端根据目的端口号，将数据报交付给正确的应用进程。

2. 差错检测（Error Detection）

  • 传输层对数据进行校验（UDP 的校验和、TCP 的校验和），检测数据在传输过程中是否出错。
  • 注意：传输层的差错检测不能纠正错误，只能检测并丢弃错误报文。

3. 提供进程级的逻辑通信

  • 对应用层隐藏了网络层的细节，进程只需使用端口号即可通信。
  • 传输层提供的是端到端的逻辑信道，而非网络层的”主机到主机”信道。

4. 拥塞控制（TCP）

  • TCP 通过拥塞窗口（cwnd）和 AIMD（加法增长乘法减少）算法控制发送速率，防止网络拥塞。
  • 这是网络层拥塞控制的重要补充。

5. 流量控制（TCP）

  • TCP 通过滑动窗口机制，根据接收方的缓存空间动态调整发送窗口大小（rwnd），防止发送方发送过快导致接收方缓存溢出。

6. 连接管理（TCP）

  • TCP 通过三次握手建立连接、四次挥手释放连接，保证面向连接服务的可靠性。

5.1.2 传输层的寻址与端口

端口的概念

端口（Port）是传输层用于标识应用进程的逻辑地址，是一个 16 位的无符号整数（0~65535）。它解决了”一台主机上同时运行多个网络应用进程”的问题。

端口号分类

类别 范围 说明 常见端口
熟知端口 0~1023 由 IANA 分配，固定分配给重要服务 HTTP(80), HTTPS(443), DNS(53), FTP(21/20), Telnet(23), SMTP(25)
登记端口 1024~49151 供用户进程或应用程序自行分配使用 需要在 IANA 注册
短暂端口 49152~65535 客户端使用，由操作系统动态分配，通信结束后释放 客户端发起连接时的源端口

常见服务与端口对应

服务 端口 协议 说明
HTTP 80 TCP 超文本传输协议（未加密）
HTTPS 443 TCP HTTP over TLS/SSL（加密）
DNS 53 UDP/TCP 域名系统，查询用 UDP，区域传输用 TCP
FTP 21（控制）/20（数据） TCP 文件传输协议
SMTP 25 TCP 简单邮件传输协议
POP3 110 TCP 邮局协议 v3
IMAP 143 TCP 互联网邮件访问协议
Telnet 23 TCP 远程登录（明文，不安全）
SSH 22 TCP 安全外壳协议（加密）
DHCP 67（服务器）/68（客户端） UDP 动态主机配置协议

套接字（Socket）

在 TCP/IP 协议中，套接字（Socket） 是端到端通信的抽象，由 IP 地址 + 端口号 组成，格式为：

\[\text{Socket} = (\text{IP 地址},\ \text{端口号})\]

  • TCP 连接 由两个端点的套接字唯一确定：连接 = (Socket_1,\ Socket_2)。
  • 例如：(192.168.1.100, 8080) → (10.0.0.1, 80)。

端口复用与分用详解

  • UDP 的分用：接收端根据 UDP 报文中的目的端口号，查找对应的套接字，将数据报交付给对应进程。如果目的端口号没有对应进程，则丢弃并发送 ICMP 端口不可达报文。
  • TCP 的分用：TCP 根据源端口 + 目的端口 + 源 IP + 目的 IP 四元组来唯一确定每个 TCP 连接（因此一个服务器进程可以同时服务多个客户端连接，每连接一对端口）。

5.1.3 无连接服务与面向连接服务

无连接服务（Connectionless Service）

代表协议：UDP（User Datagram Protocol）

UDP 提供无连接的、不可靠的、面向报文的传输服务。

UDP 的特点

  1. 无连接：发送数据前不需要建立连接，直接发送数据报。
  2. 不可靠：不保证数据报一定能到达目的主机，也不保证按序到达，更不保证不重复。
  3. 面向报文：对应用层交付的报文既不合并也不拆分，保留边界。发送端 UDP 给报文添加首部后直接交给 IP 层。
  4. 无拥塞控制：UDP 发送速率完全由应用层决定，网络拥塞不影响 UDP 的发送行为（因此 UDP 可能加剧网络拥塞）。
  5. 首部开销小：UDP 首部仅 8 字节。

UDP 适用场景

  • 实时性要求高、可靠性要求低的应用：如视频流媒体、语音通话（VoIP）、在线游戏、DNS 查询、SNMP 等。
  • 简短请求/响应：一次往返即可完成的应用，如 DNS。
  • 多播/广播支持：UDP 支持一对一、一对多、多对多等通信模式。

面向连接服务（Connection-Oriented Service）

代表协议：TCP（Transmission Control Protocol）

TCP 提供面向连接的、可靠的、字节流的传输服务。

TCP 的特点

  1. 面向连接：数据传输前必须经过三次握手建立连接，传输结束后四次挥手释放连接。
  2. 可靠传输：通过确认应答（ACK）、超时重传、序号机制、校验和等手段，保证数据无差错、不丢失、不重复、按序到达。
  3. 字节流服务：TCP 将应用层交付的数据视为无结构的字节流，不保留应用层报文的边界。TCP 将字节流分段后发送，接收端将收到的字节流按序拼接成字节流交付给应用层。
  4. 全双工：连接双方可以同时发送和接收数据。
  5. 首部较大：TCP 首部至少 20 字节（不含选项字段时）。

TCP 适用场景

  • 要求可靠传输的应用：如网页浏览（HTTP/HTTPS）、文件传输（FTP）、电子邮件（SMTP/POP3/IMAP）、远程登录（SSH）等。
  • 大数据量传输：需要对数据进行可靠排序和重传的应用。

UDP vs TCP 对比（考研核心）

对比维度 UDP TCP
连接性 无连接 面向连接（三次握手/四次挥手）
可靠性 不可靠，不保证到达 可靠，保证按序无差错到达
服务类型 面向报文 面向字节流
传输速率 高效，无拥塞控制 相对较低，有流量/拥塞控制
首部开销 8 字节 至少 20 字节（可带选项）
资源消耗 小（无连接状态） 大（维护连接状态）
支持广播/组播 支持 不支持（仅单播）
错误检测 校验和（可选） 校验和（必须）+ 确认应答

二、UDP 协议

5.2.1 UDP 数据报

UDP 概述

UDP（User Datagram Protocol，用户数据报协议）是传输层的重要协议之一，提供无连接的、不可靠的、面向报文的传输服务。它是 IP 服务的”简单增强”，在 IP 数据报之上仅增加了复用/分用和差错检测功能。

UDP 数据报格式

UDP 数据报由首部和数据两部分组成。首部固定 8 字节，格式如下：

首部各字段详解

字段 长度 说明
源端口号 16 bit 发送端端口号，需要对方回信时可用。不需要时设为 0。
目的端口号 16 bit 接收端端口号，必填字段，决定了 UDP 数据报的交付目标。
UDP 长度 16 bit UDP 数据报的总长度（首部 + 数据），单位为字节，最小值为 8。
UDP 校验和 16 bit 可选字段。填 0 表示不计算校验和，填非零则包含校验信息。检测数据在传输过程中的比特错误。

UDP 数据报封装

UDP 的”尽力而为”特性

UDP 不保证数据报能够： 1. 不丢失：无确认应答机制，丢失后发送方不知道。 2. 不重复：无序号机制，可能收到重复数据报。 3. 按序到达：无序号和排序机制，到达顺序可能乱序。 4. 可靠传输：无重传、流量控制、拥塞控制机制。

UDP 长度字段与 IP 封装的关系

UDP 数据报在封装成 IP 数据报时，IP 首部的协议字段值为 17（表示 UDP）。UDP 长度字段的值应该等于 IP 数据报中 UDP 数据的总长度（即 IP 数据部分的长度）。

5.2.2 UDP 校验和

UDP 校验和的作用

UDP 校验和用于检测 UDP 数据报在传输过程中是否发生了比特错误（即 0/1 翻转）。这是一种端到端的差错检测机制，发送端计算校验和并填入字段，接收端重新计算并比对。

注意：UDP 校验和是可选的，但推荐使用。若校验和字段为 0，表示发送方未计算校验和；为非零值时必须携带正确的校验结果。

UDP 校验和的计算范围——伪首部

UDP 校验和的计算比较特殊，除了 UDP 首部和 UDP 数据部分外，还包含一个伪首部（Pseudo Header）。伪首部是从 IP 首部中提取的字段，用于验证”数据是否交付给了正确的 IP 地址”。

伪首部格式（12 字节）

  • 协议号：对于 UDP 为 17（与 IP 首部 Protocol 字段值相同）。
  • UDP 长度：UDP 首部 + 数据的总长度（伪首部不包含在 UDP 数据报中，只是参与校验计算）。

校验和计算步骤

  1. 构造伪首部：提取源 IP、目的 IP，填入协议号和 UDP 长度。
  2. 按 16 位分组：将伪首部（12 字节）+ UDP 首部（8 字节）+ 数据部分，每 16 位分成一组（共 \(6 + 4 + N\) 组）。
  3. 反码求和：对所有 16 位分组进行二进制反码求和（即逐组相加，若最高位有进位则回卷加到最低位）。
  4. 取反码：最终结果取反码，即得到校验和。
  5. 发送：将校验和填入 UDP 首部的校验和字段发送。
  6. 接收验证：接收方用相同方法计算，若结果为全 1（即 0xFFFF），则认为正确。

为什么 UDP 要包含伪首部？

为了防止 UDP 数据报被误交付到错误的主机。例如：某主机本来应该接收来自 IP_A 的 UDP 数据，但因路由错误收到了来自 IP_B 的数据（IP_B 上的攻击者伪造了源 IP）。此时接收端计算校验和时，伪首部的源 IP 是假的（IP_A），与接收端记录的 IP 不同，校验和会检测到错误并丢弃该报文，从而提供了一定的安全保障。

三、TCP 协议

5.3.1 TCP 的特点

TCP 协议概述

TCP（Transmission Control Protocol，传输控制协议）是传输层最重要的协议之一，提供面向连接的、可靠的、全双工的、字节流传输服务。它是 Internet 上大多数应用（Web、Email、FTP 等）的基础。

TCP 的核心特点

1. 面向连接

  • 传输数据前必须先建立连接（三次握手），传输结束后释放连接（四次挥手）。
  • TCP 连接的建立和释放过程涉及状态转换（CLOSED、LISTEN、SYN_SENT、SYN_RCVD、ESTABLISHED、FIN_WAIT_1、FIN_WAIT_2、CLOSE_WAIT、LAST_ACK、TIME_WAIT 等）。

2. 可靠传输

TCP 通过以下机制保证可靠性： - 确认应答（ACK）：接收方收到数据后发送 ACK 确认。 - 超时重传：发送方在一定时间内未收到 ACK，则重传数据。 - 序号机制：每个字节都有序号，支持数据有序交付和丢失检测。 - 校验和：检测数据传输中的比特错误。 - 去重：接收方根据序号去除重复数据。

3. 字节流服务

  • TCP 将应用层交付的数据视为无结构的字节流，不保留应用层报文的边界。
  • 发送端：应用层写入的”报文”可能被 TCP 分成多个 TCP 报文段发送；也可能将多个小”报文”合并成一个 TCP 报文段发送（Nagle 算法等优化）。
  • 接收端：TCP 将收到的字节流按序拼接，交付给应用层。
  • 这与 UDP 的”面向报文”形成鲜明对比：UDP 保留应用层报文的边界，每个写操作对应一个 UDP 数据报。

4. 全双工（Full-Duplex）

  • TCP 连接是全双工的：连接双方可以同时发送和接收数据。
  • 每一方都有各自的发送缓存、接收缓存、发送序号、接收序号。

5. 流量控制

  • TCP 通过滑动窗口机制控制发送方的发送速率，防止接收方缓存溢出。
  • 接收方通过 TCP 首部中的窗口大小（Window Size）字段告知发送方当前可接收的数据量。

6. 拥塞控制

  • TCP 根据网络的拥塞程度，通过拥塞窗口（cwnd）动态调整发送速率。
  • 拥塞控制算法包括：慢启动、拥塞避免、快恢复。

TCP 与 UDP 核心对比

特性 TCP UDP
连接性 面向连接 无连接
可靠性 可靠 不可靠
传输单元 字节流 报文段（保留边界）
首部长度 最小 20 字节 8 字节
流量控制 有（rwnd） 无
拥塞控制 有（cwnd） 无
传输速率 相对较低 高效
适用场景 HTTP、FTP、SMTP DNS、视频、VoIP
状态复杂性 高（有连接状态） 低（无连接状态）

TCP 连接与资源消耗

  • TCP 连接由四元组唯一确定：(源 IP, 源端口, 目的 IP, 目的端口)。
  • 服务器端通常维护一个监听套接字（listen socket），接受多个连接请求，每个新连接分配一个新的已连接套接字（connected socket）。
  • 服务器可同时服务的 TCP 连接数受限于文件描述符数量和内存资源。

5.3.2 TCP 报文段

TCP 报文段结构

TCP 报文段（TCP Segment）是 TCP 传输的基本单位，由 TCP 首部 和 数据（可选） 两部分组成。TCP 报文段封装在 IP 数据报中，通过 IP 协议传输。

TCP 首部格式（20 字节，固定）

TCP 首部各字段详解

字段 长度 说明
源端口号 16 bit 发送端 TCP 进程的端口号
目的端口号 16 bit 接收端 TCP 进程的端口号
序号（Sequence Number） 32 bit 本报文段所发送数据的第一个字节在整个字节流中的编号。SYN 标志占用一个序号。
确认号（ACK Number） 32 bit 期望收到的下一个字节的序号（即该序号之前的所有字节均已正确接收）。只有 ACK 标志为 1 时确认号才有效。
数据偏移（Data Offset） 4 bit TCP 首部的长度，单位为 4 字节。最小值为 5（无选项字段时 = 20 字节），最大值为 15（带选项字段时 ≤ 60 字节）。
保留（Reserved） 6 bit 保留供将来使用，目前必须置为 0。
控制标志（Control Flags） 6 bit URG、ACK、PSH、RST、SYN、FIN（详见下表）
窗口大小（Window Size） 16 bit 接收方当前允许发送方发送的字节数（接收缓存空间），用于流量控制。单位为字节。
校验和（Checksum） 16 bit TCP 伪首部 + TCP 首部 + 数据的校验和（必须计算）。
紧急指针（Urgent Pointer） 16 bit 仅在 URG=1 时有效，指示紧急数据在报文段中的结束位置（最后一个紧急字节的序号）。
选项（Options） 0~40 字节 可选字段，用于协商 MSS（Maximum Segment Size）、窗口扩展、时间戳、SACK 等功能。

六种控制标志（重要）

标志 名称 含义
URG Urgent 紧急指针有效，表示报文段中包含紧急数据（需紧急发送），紧急数据从报文段首部开始，长度由紧急指针指示。
ACK Acknowledgment 确认号有效，表示确认号字段值是有效的（除第一个 SYN 报文段外，所有报文段 ACK 标志均置 1）。
PSH Push 催促接收方立即将数据交付给应用层，不要在接收缓存中停留（通常用于交互式应用）。
RST Reset 重置连接，用于异常情况下的连接终止（如收到无法处理的报文段）。
SYN Synchronize 同步序号，仅在建立 TCP 连接的第一个报文段中置 1（SYN 占用一个序号）。
FIN Finish 结束标志，仅在拆除 TCP 连接的最后一个报文段中置 1（FIN 占用一个序号）。

序号与确认号的工作原理（核心）

  • 序号：seq=x 表示”本报文段从第 x 个字节开始发送，共发送 len 个字节”。
  • 确认号：ack=y 表示”已正确收到前 y-1 个字节，期望收到第 y 个字节”。
  • 例如：客户端发送 seq=1000, len=500 的数据，服务器正确接收后回复 ACK=1, ack=1500（表示期望下一个收到 1500）。

TCP 伪首部（参与校验和计算）

MSS（Maximum Segment Size）

MSS 是 TCP 选项字段中的重要参数，表示 TCP 报文段中数据部分的最大长度（不含 TCP 首部）。MSS 在连接建立时协商，通常为： - 以太网环境下：MSS = 1460 字节（MTU 1500 - IP 首部 20 - TCP 首部 20） - 典型值：1460 字节（以太网）、536 字节（最小 MTU）

5.3.3 TCP 连接管理

TCP 连接管理概述

TCP 是面向连接的协议，连接管理包括建立连接（三次握手） 和释放连接（四次挥手） 两个过程。连接管理涉及复杂的状态转换，是网络编程和故障排查的基础。

三次握手（Three-Way Handshake）

建立 TCP 连接的过程需要三次报文交互：

三次握手详细过程

步骤 发送方 报文内容 客户端状态 服务器状态
① 客户端 SYN=1, seq=x SYN_SENT —
② 服务器 SYN=1, ACK=1, seq=y, ack=x+1 — SYN_RCVD
③ 客户端 ACK=1, seq=x+1, ack=y+1 ESTABLISHED ESTABLISHED

为什么需要三次握手？

  1. 同步双方的初始序号：客户端发送 seq=x，服务器回复 ack=x+1（确认收到）并发送自己的 seq=y；客户端回复 ack=y+1（确认收到服务器的序号）。三次握手确保双方都确认了对方的序号。
  2. 防止历史连接初始化浪费资源：如果只进行两次握手，服务器收到旧连接（SYN=1, seq=x_old）的请求后，无法判断这是历史连接，会建立连接并等待客户端发送数据，造成资源浪费。三次握手中，客户端会检查 ack 是否正确（是否为 y+1），若不是则发送 RST 拒绝连接。
  3. 确保双方都有发送和接收能力：三次握手证明了一个完整的请求-响应循环。

四次挥手（Four-Way Wavehand）

关闭 TCP 连接需要四次报文交互（由于 TCP 全双工特性，每一方都需要单独关闭）：

四次挥手详细过程

步骤 发送方 报文内容 客户端状态 服务器状态
① 客户端 FIN=1, seq=u FIN_WAIT_1 —
② 服务器 ACK=1, ack=u+1 FIN_WAIT_2 CLOSE_WAIT
③ 服务器 FIN=1, seq=v — LAST_ACK
④ 客户端 ACK=1, ack=v+1 TIME_WAIT CLOSED

为什么需要四次挥手？

  • TCP 是全双工的，每个方向都需要单独关闭。客户端发送 FIN 表示”我不再发送数据了”（但仍能接收），服务器回复 ACK 确认；然后服务器也发送 FIN 表示”我也不发送了”，客户端回复 ACK 确认。
  • 关闭服务器到客户端方向的连接需要单独的一次 FIN 和一次 ACK。

TIME_WAIT 状态与 2MSL

  • 客户端发送最后的 ACK 后，进入 TIME_WAIT 状态，等待 2MSL（Maximum Segment Lifetime） 才进入 CLOSED。
  • MSL 是任何 IP 数据报在网络中存在的最大时间，通常为 2 分钟。
  • 2MSL 的作用：
    1. 确保最后的 ACK 能到达服务器：如果 ACK 丢失，服务器会在 2MSL 内重发 FIN，客户端可以再次发送 ACK。
    2. 让本连接的所有报文段在网络中消失：防止旧连接的延迟报文被新连接误接收。

TCP 状态转换图（简化版）

SYN Cookie（防 SYN 洪泛攻击）

服务器在收到 SYN 后，不立即分配资源，而是根据 SYN 信息计算一个特殊的序号（Cookie）作为 server_isn 回复给客户端。直到收到客户端的第三个握手报文（ACK）后，才分配连接资源。这可以有效防御 SYN Flooding 攻击。

RST 标志与异常连接终止

  • 收到 RST=1 的报文段后，连接立即终止，不需要四次挥手。
  • 常见场景：访问不存在的端口、服务器崩溃后客户端重连、应用强制终止等。

5.3.4 TCP 可靠传输

可靠传输概述

TCP 通过多种机制共同保证数据的可靠传输：无差错、不丢失、不重复、按序到达。

1. 序号机制

  • TCP 将每个字节编号，序号（seq）表示”本报文段第一个字节的数据在整个字节流中的位置”。
  • 例如：客户端发送 1000 字节的数据，分成两个报文段：第一个 seq=0, len=500；第二个 seq=500, len=500。
  • 序号为 32 位无符号数，循环使用。

2. 确认应答（ACK）机制

  • 接收方收到数据后，发送 ACK 确认。确认号（ack）表示”期望收到的下一个字节序号”。
  • 累计确认（Cumulative ACK）：TCP 只确认按序收到的最后一个字节，ACK 丢失时不需要重传。例如：收到 0~1000 的所有字节，回复 ack=1001；即使中间 500~600 的 ACK 丢失，ack=1001 仍然有效。

3. 超时重传（Retransmission Timeout, RTO）

  • 发送方发送数据后，启动定时器，等待 ACK。
  • 若在超时时间内未收到 ACK，则认为数据丢失，重传该报文段。
  • RTO 的计算：RTO 不能设置过小（频繁重传），也不能过大（性能下降）。TCP 使用自适应算法：

\[ RTT_s \leftarrow (1-\alpha) \times RTT_s + \alpha \times RTT_{new} \]

\[ RTT_D \leftarrow (1-\beta) \times RTT_D + \beta \times |RTT_{new} - RTT_s| \]

\[ RTO = RTT_s + 4 \times RTT_D \]

常用参数：\(\alpha = 1/8\)，\(\beta = 1/4\)。

4. 快速重传（Fast Retransmit）

  • 当发送方收到3 个重复 ACK（即同一 ACK 被重复收到），说明接收方期望的数据未收到（可能丢失），发送方不等超时，立即重传该数据。
  • 快速重传比超时重传更快，能减少等待时间。

5. SACK（Selective Acknowledgment，选择确认）

  • 传统的累计确认只能确认按序到达的最后一个字节，即使收到非连续的数据块也只能报告一个 ACK。
  • SACK 允许接收方告诉发送方”我收到了哪些非连续的数据块”，发送方只需重传丢失的部分，而非重传整个窗口。
  • SACK 通过 TCP 选项字段携带，占用最多 40 字节。

可靠传输流程（发送方视角）

重传时间计算示例

若 RTT 测量值为 100ms，RTT_s = 100ms，RTT_D = 10ms，则：

\[RTO = 100 + 4 \times 10 = 140 \text{ ms}\]

实际中 RTO 通常至少为 1 秒（最小值）。

5.3.5 TCP 流量控制

流量控制概述

流量控制（Flow Control）是 TCP 提供的机制，防止发送方发送过快导致接收方缓存溢出。与拥塞控制（防止网络拥塞）不同，流量控制解决的是发送方与接收方速度匹配的问题。

滑动窗口机制（Sliding Window）

TCP 流量控制基于滑动窗口协议。接收方在每个 ACK 报文中通过窗口大小（rwnd）字段告知发送方当前可接收的字节数。

工作原理

  1. 接收方维护 接收窗口（rwnd），表示其缓存中可用空间大小。
  2. 发送方根据接收方通告的 rwnd，限制自己未确认数据的最大字节数。
  3. 接收方每成功交付数据给应用层，rwnd 增大，发送更新后的窗口大小。

零窗口（Zero Window）与窗口更新

  • 当接收方缓存满时（rwnd = 0），发送方必须停止发送数据。
  • 接收方处理完数据后，发送 窗口更新（Window Update） 报文（ACK + 新的 rwnd > 0），告知发送方可以继续发送。
  • 若窗口更新报文丢失，可能导致死锁（双方相互等待）。TCP 使用持续计时器（Persistence Timer） 解决：发送方收到零窗口后启动计时器，超时后发送窗口探测（Window Probe） 报文，强制对方回复 ACK。

流量控制与拥塞控制的区别（重要）

维度 流量控制 拥塞控制
目的 防止发送方压垮接收方 防止发送方压垮整个网络
依据 接收方缓存空间（rwnd） 网络拥塞程度（cwnd）
机制 滑动窗口 慢启动、拥塞避免、快恢复
控制者 接收方 发送方（根据网络反馈）
窗口 接收窗口 rwnd 拥塞窗口 cwnd
实际窗口 min(rwnd, cwnd) —

发送窗口的实际大小

\[\text{发送窗口} = \min(\text{rwnd}, \text{cwnd})\]

即发送方的发送速率受接收窗口和拥塞窗口两者的共同制约。

糊涂窗口综合征（Silly Window Syndrome）

当接收方每次只腾出少量空间（如 1 字节）就通告给发送方，发送方也只发送 1 字节，导致网络效率极低。

解决方法（Nagle 算法 / Clark 解决方法）： - 接收方：只在自己缓存空间达到 MSS 或一半时才通告非零窗口。 - 发送方：等待收集足够数据或收到 ACK 后再发送（Nagle 算法）。

5.3.6 TCP 拥塞控制

拥塞控制概述

拥塞控制（Congestion Control）是 TCP 防止网络拥塞、保证网络稳定运行的重要机制。当网络中出现过多数据分组导致性能下降（延迟增大、丢包增加）时，拥塞控制机制会减少发送方的发送速率。

拥塞与流量的区别

  • 流量控制：端到端的速度匹配问题，关心的是接收方能否接得住。
  • 拥塞控制：全局的网络资源问题，关心的是网络能否承载得了。

两者协同工作，发送方的发送窗口 = min(rwnd, cwnd)。

拥塞窗口（Congestion Window, cwnd）

  • cwnd 是发送方维护的一个变量，表示发送方在收到 ACK 之前可以发送的最大数据量（字节）。
  • cwnd 由发送方根据网络拥塞程度动态调整。
  • 调整策略分为三个阶段：慢启动 → 拥塞避免 → 快恢复。

慢启动（Slow Start）

核心思想：TCP 连接建立初期，cwnd 从一个很小的值（通常为 1 MSS = Maximum Segment Size）开始，每收到一个 ACK，cwnd 增加一个 MSS，即指数增长。

规则： - 每收到 1 个 ACK：\(cwnd = cwnd + 1 \times MSS\) - 等价于：每经过 1 个 RTT：\(cwnd = cwnd \times 2\)

慢启动门限（ssthresh）： - 当 cwnd 达到 ssthresh 时，进入拥塞避免阶段。 - ssthresh 的初始值通常很大（如 65535 字节），在拥塞发生时动态更新。

拥塞避免（Congestion Avoidance）

核心思想：进入拥塞避免阶段后，cwnd 改为线性增长，每个 RTT 仅增加 1 个 MSS（加法增长），避免快速增长导致拥塞。

规则： - 每收到 1 个 ACK：\(cwnd = cwnd + 1 \times \frac{MSS}{cwnd}\) - 等价于：每经过 1 个 RTT：\(cwnd = cwnd + 1 \times MSS\)

快重传（Fast Retransmit）

当发送方收到 3 个重复 ACK（表明接收方期望的数据丢失），立即重传丢失的数据报文段，不等待超时。

快恢复（Fast Recovery）

快恢复是快重传之后的处理策略： 1. 收到 3 个重复 ACK 后，cwnd 设为 ssthresh = cwnd / 2（乘法减少）。 2. 然后 cwnd = ssthresh + 3 × MSS（因为收到了 3 个 ACK，说明有 3 个数据已离开网络）。 3. 进入拥塞避免阶段（线性增长）。

超时重传 vs 3-ACK 重传

场景 处理方式 cwnd 变化 ssthresh 变化
超时 慢启动 cwnd = 1 MSS ssthresh = cwnd / 2，重新慢启动
3 个重复 ACK 快重传 + 快恢复 cwnd = ssthresh + 3×MSS ssthresh = cwnd / 2，进入快恢复

拥塞控制算法流程（AIMD）

阶段 条件 cwnd 增长方式 名称
慢启动 cwnd < ssthresh 每 RTT 翻倍（指数） 指数增长
拥塞避免 cwnd ≥ ssthresh 每 RTT 加 1（线性） 加法增长
超时 — cwnd = 1 MSS 乘法减少
3-ACK — cwnd = ssthresh + 3×MSS 乘法减少

AIMD（Additive Increase Multiplicative Decrease）

  • 加法增长（Additive Increase）：拥塞避免阶段，每 RTT cwnd 增加 1 MSS。
  • 乘法减少（Multiplicative Decrease）：发生拥塞时，cwnd 减半（ssthresh 设为当前 cwnd 的一半）。
  • AIMD 确保多个 TCP 连接最终收敛到公平共享网络带宽。

TCP Reno vs TCP Tahoe

版本 超时处理 3-ACK 处理
TCP Tahoe cwnd=1 MSS，重新慢启动 快重传后进入快恢复（cwnd 减半）
TCP Reno cwnd=1 MSS，重新慢启动 快重传后进入快恢复（cwnd 减半后线性增长）

TCP Reno 在 3-ACK 场景下性能更好（不需要重新慢启动）。
